<h1>Getting Started</h1>

<h3>Introduction</h3>

<p>Sestra is an access middleware for modern APIs and automated systems. It converts verified conditions into short-lived access sessions without managing user identity, credentials, or sensitive data. Sestra is built for environments where:</p>

<ul>
  <li>APIs are consumed by machines</li>
  <li>access must be temporary</li>
  <li>privacy and compliance matter</li>
</ul>

<p>Sestra focuses on one responsibility only: deciding whether access should be granted right now.</p>

<h1>Problem Statement</h1>

<p>Modern APIs are increasingly consumed by backend services, bots, and autonomous agents. However, access control and monetization models still rely on:</p>

<ul>
  <li>user accounts</li>
  <li>long-lived credentials</li>
  <li>identity-centric billing</li>
</ul>

<p>This creates:</p>

<ul>
  <li>operational complexity</li>
  <li>data liability</li>
  <li>compliance overhead</li>
  <li>friction for automated clients</li>
</ul>

<p>Sestra exists to remove these constraints.</p>

<h1>Design Principles</h1>

<p>Sestra is built on the following principles:</p>

<ul>
  <li>Access over identity</li>
  <li>Sessions over credentials</li>
  <li>Configuration over custom logic</li>
  <li>Privacy by non-collection</li>
  <li>Minimal system surface area</li>
</ul>

<p>Every architectural decision in Sestra follows these rules.</p>

<h1>Key Technologies</h1>

<p>Sestra is built on a set of core technical principles that prioritize simplicity, security, and privacy.<br />
Rather than introducing new protocols or complex infrastructure, Sestra combines proven system design patterns into a focused access framework.</p>

<p>Below are the key technologies and design approaches that make Sestra work.</p>

<h3>Session-Based Access Control</h3>

<p>At the core of Sestra is a session-based access model.</p>

<p>Instead of relying on:</p>

<ul>
  <li>user accounts</li>
  <li>permanent credentials</li>
  <li>long-lived API keys</li>
</ul>

<p>Sestra issues short-lived access sessions.</p>

<p>Each session:</p>

<ul>
  <li>is created only after requirements are met</li>
  <li>has a defined expiration time</li>
  <li>cannot be reused once expired</li>
</ul>

<p>This approach reduces risk and simplifies access management for both humans and automated systems.</p>

<h3>External Verification Signals</h3>

<p>Sestra does not generate or manage verification data itself. Instead, it evaluates verification signals produced by external systems.<br />
These signals indicate whether predefined conditions have been fulfilled.</p>

<p>Sestra only checks the result of verification, not the underlying data. This keeps Sestra lightweight and avoids unnecessary data handling.</p>

<h3>Policy-Driven Decision Engine</h3>

<p>Access decisions in Sestra are driven by policies. A policy defines:</p>

<ul>
  <li>what condition must be met</li>
  <li>how long access should last</li>
  <li>how many requests are allowed within a session</li>
</ul>

<p>Policies are evaluated in real time for each request.<br />
They are independent of user identity and do not require stored profiles.</p>

<h3>Event-Based Architecture</h3>

<p>Sestra communicates with your backend through events.</p>

<p>Key lifecycle events include:</p>

<ul>
  <li>session created</li>
  <li>verification confirmed</li>
  <li>access granted</li>
  <li>session expired</li>
</ul>

<p>This event-based model allows:</p>

<ul>
  <li>clean integration</li>
  <li>asynchronous processing</li>
  <li>easy observability without exposing sensitive data</li>
</ul>

<h3>Privacy by Non-Collection</h3>

<p>Sestra achieves privacy by design, not by obfuscation.</p>

<p>The system is intentionally built to avoid collecting:</p>

<ul>
  <li>user identity</li>
  <li>network identifiers</li>
  <li>behavioral history</li>
  <li>raw verification artifacts</li>
</ul>

<p>By minimizing data collection, Sestra reduces both security and compliance risk.</p>

<h3>Stateless Middleware Design</h3>

<p>Sestra operates as a stateless decision layer.</p>

<p>It does not:</p>

<ul>
  <li>execute workloads</li>
  <li>store application data</li>
  <li>maintain user profiles</li>
</ul>

<p>Its responsibility is limited to:</p>

<ul>
  <li>evaluating access conditions</li>
  <li>managing session lifecycle</li>
  <li>issuing access decisions</li>
</ul>

<p>This design makes Sestra easy to scale and simple to audit.</p>

<h3>Built for Automated Systems</h3>

<p>Sestra is designed for environments where:</p>

<ul>
  <li>requests are generated by software</li>
  <li>access is programmatic</li>
  <li>identity is not always available or relevant</li>
</ul>

<p>The framework supports:</p>

<ul>
  <li>backend-to-backend communication</li>
  <li>autonomous agents</li>
  <li>machine-driven workflows</li>
</ul>

<p>Without introducing additional friction or identity requirements.</p>

<h1>Why These Technologies Matter</h1>

<p>Together, these technologies allow Sestra to remain:</p>

<ul>
  <li>focused on access control</li>
  <li>lightweight to integrate</li>
  <li>safe for privacy-sensitive environments</li>
  <li>suitable for enterprise use</li>
  <li>adaptable to future verification methods</li>
</ul>

<p>Sestra does not depend on any single technology choice.<br />
It is designed to remain flexible as verification methods evolve.</p>

<h1>Architecture Overview</h1>

<p>Sestra is built as a lightweight access middleware with clear boundaries.<br />
It evaluates verification results, issues short-lived sessions, and informs your backend through events.</p>

<p>Sestra does not store identity, does not process funds, and does not execute workloads.<br />
Its only job is access decision-making.</p>

<h1>Workflows</h1>

<h3>Workflow A: Single-Use Access</h3>

<p>One verified fulfillment grants one session with a short TTL.</p>

<p>After expiration, a new session is required.</p>

<h3>Workflow B: Multi-Call Access</h3>

<p>A policy may allow multiple calls within a TTL window.</p>

<p>Usage is enforced by session policy rules.</p>

<h3>Workflow C: Automated Clients</h3>

<p>Automated systems request, fulfill, and reuse sessions until expiration, without login flows.</p>
